# Java PolicyNIM as a Qodo-Reviewed PR Train

## Summary

- Treat this as a greenfield Java repo with one seed commit on `main`, then a sequence of small draft PRs that Qodo can review individually.
- Target stack: Java 21, Maven, Spring Boot 3.x, Spring MVC, official MCP Java SDK, Spring Security, Flyway, Spring JDBC, Postgres + `pgvector`, Testcontainers, JUnit 5, AssertJ, ArchUnit, Cucumber JVM.
- Keep the external MCP surface stable where it matters: `policy_search`, `policy_preflight`, `/mcp`, `/healthz`.
- Current blocker: this project directory started without git, so `qodo-get-rules` cannot run until repo init and remote setup are done.

## Git Repo Initialization

- Create the GitHub repo first, preferably named `java-policynim`.
- Initialize locally with `git init -b main`, add `origin`, and push one seed commit before any implementation PRs.
- Seed commit should be minimal so every real code change can go through PR review:
  - Commit: `chore: initialize repository metadata`
  - Contents: `README.md`, `.gitignore`, `LICENSE`, `.editorconfig`, `.gitattributes`
- After the seed push, enable:
  - GitHub Actions
  - Qodo app/integration for PR review
  - Branch protection on `main`
  - Required checks: `unit`, `integration`, `acceptance`, `archunit`, `package`
- Review loop for every PR:
  - Create feature branch from `main`
  - Run `qodo-get-rules` before coding
  - Code test-first
  - Push branch and open draft PR
  - Wait for Qodo review
  - Resolve findings with `qodo-pr-resolver` or `qodo-fix`
  - Merge only after CI is green and Qodo findings are addressed or explicitly deferred

- Use one Maven module now; enforce boundaries with ArchUnit instead of splitting modules prematurely.
- Use `io.policynim` as the default Java package and Maven `groupId`.
- Use Flyway migrations plus Spring JDBC, not JPA.
- Keep transport code in `mcp`, domain parsing in `policy`, orchestration in `ingest` / `retrieval` / `preflight`, and all NVIDIA-specific code in `provider.nvidia`.

## Skills To Use

- Most useful installed skills for this project:
  - `qodo-get-rules`: load repo-scoped Qodo rules before each PR implementation
  - `qodo-pr-resolver`: primary workflow after Qodo comments land on each PR
  - `qodo-fix`: simpler fallback for reading or fixing Qodo review issues
  - `failure-path-testing`: critical for auth rejection, readiness failure, malformed input, and fail-closed preflight cases
  - `dx-audit`: use on README, setup docs, CLI/help text, and operator-facing error messages
  - `github:yeet`: useful when publishing branches and opening draft PRs
  - `github:gh-fix-ci`: use only when Actions checks fail
- Important gap:
  - There is no dedicated Java/Spring implementation skill installed, so Java conventions need to be enforced through repo docs, ArchUnit tests, and Qodo rules.

## TDD and BDD Strategy

- TDD is mandatory for every PR:
  - First commit in each PR is a `test:` commit
  - Second commit makes the tests pass
  - Third commit is docs/refactor only if needed
- Keep PRs at 2-3 commits max so Qodo reviews remain focused.
- Use JUnit 5 + AssertJ for unit and service tests.
- Use Testcontainers for all persistence and hosted HTTP integration tests.
- Use ArchUnit in PR1 onward to enforce package boundaries continuously.
- Use Cucumber only for top-level behavior and acceptance flows; do not use it for low-level unit tests.
- Apply the `failure-path-testing` skill deliberately on PR5 and PR6, and whenever Qodo flags missing negative-path coverage.

## Assumptions

- Git provider is GitHub.
- Maven and single-module layout are intentional, not temporary.
- One non-PR seed commit on `main` is acceptable so every meaningful implementation step can be reviewed through PRs.
- Qodo review is part of the process gate for every PR after the seed commit.
- Full parity with the Python beta portal, API-key DB, quota system, runtime evidence, and eval framework remains out of scope for this PR train.
