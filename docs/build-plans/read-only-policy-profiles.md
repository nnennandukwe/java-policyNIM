## Package Layout And Component Design

1. In `policy/catalog`, parse profile TOML with the existing pinned Tomlj reader. Share TOML decoding where the two contracts agree. Report profile errors using their own field locations. Build the typed profile and normalized pin data in declaration order. Unknown fields and wrong types fail before pack access.
2. Let `PackSourceFiles` and the bundled reader supply the manifest and selected original member bytes to the same catalog builder. For profile loading, return the pack ID/version, standalone entries and the parsed runtime rules by policy ID. The current `Builder.addPackMember` drops `ParsedSource.rules()`. Retain those rules from the same parse and byte capture used to construct each entry. Require a manifest for every selected pack. Track canonical root identities separately from the selector spelling used in the public pin. Topic member paths are relative to that topic manifest. The root's aggregate manifest assigns different provenance and paths to the same Markdown.
3. Reuse `CatalogJson` for entry serialization and digesting. Resolve every pin before applying decisions. Reject duplicate pack IDs, repeated resolved directories and duplicate policy IDs across packs. Retain the original entry's target digest and metadata when prefixing its path with `pack_id/`. Validate every replacement/exclusion against the original target digest. Reject repeated targets or replacement IDs, missing policies, chains, cycles and an empty effective set.
4. Check declared conflicts against the remaining active IDs. Compare active runtime matcher keys by action, sorted unique path globs, sorted unique command regexes and sorted unique lowercased URL hosts. Rule reasons, effect and line spans are outside the matcher key. Two different effects for the same key fail. Preserve excluded and replaced entries, reasons and bodies in preview and show. Return authored/effective counts separately, empty unlisted Markdown, source scope and null generation/index counts.
5. Route the two explicit profile subcommands to that resolver before Spring startup. Use the existing CLI text and JSON formatting conventions and exit 1 for source errors. Profile validation returns `status`, `catalog_digest`, `effective_count` and the reference's `limits` text. The existing `policies validate --source` command retains its own catalog-validation envelope. ## Canonical Contracts

Use UTF-8 compact JSON with the model field order, explicit defaults and nulls. Hash with SHA-256 and publish lowercase hex with the `sha256:` prefix. The standalone policy revision hashes the complete active catalog entry before path prefixing. The pack pin hashes the LF-joined standalone entries in Unicode scalar policy-ID order. A decision's expected digest is the entry's target digest. These three hashes serve different callers.

The profile digest hashes the normalized current profile. Its fields run in the order `schema_version, profile_id, packs, exclusions, replacements, conflicts`. Each pin uses `path, pack_id, version, digest, policies`. Keep pack and decision list order. Rebuild each policy map in scalar policy-ID order. The catalog hashes the UTF-8 profile digest, LF and LF-joined compact composed entries in policy-ID order, with no trailing LF. The public `pack_pins` records omit the per-policy map. [Profile identity](https://github.com/nnennandukwe/policyNIM/blob/fcc5322a6672b0275dcc6e0c299e631df8e8de19/src/policynim/services/profiles.py#L347-L362)

## Follow-on Builds

A second review unit can add `init` and `diff`. Init must publish a new profile without overwriting an existing one. A default Java profile needs a durable selector readable by both installations. Diff compares revisions by pack ID and policy ID, returns the current authored entries before decisions, and can succeed with a blocking `validation_error`. Its review token hashes the original profile text after universal newline decoding, LF and the compact current pin model. Changing comments or TOML key order invalidates that token. LF-to-CRLF conversion alone preserves it. The six fixtures verify those outcomes on the installed wheel.

Give `update` a separate transaction-proof build. It must preserve untouched TOML comments and decision formatting, revalidate before atomic publication under a cooperating-writer lock, and distinguish precommit failure from postcommit durability or cleanup warnings. Check removed pins, quoted and Unicode keys, file modes and Windows lock behavior. Later generation capture must store the protected source snapshot, revalidate pins from retained data and send only effective documents to retrieval and rules.
